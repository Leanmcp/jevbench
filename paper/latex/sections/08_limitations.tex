\section{Limitations}
\label{sec:limitations}

\begin{enumerate}
  \item \textbf{The commercial system is a black box.} We reach Jev~1.13.0 only
  through its HTTP API. Its architecture, parameter count, tokenizer, training
  data and serving configuration are unpublished. The only version
  identifier available is the returned model string, so we cannot exclude
  server-side changes between our run and a replication. We also cannot determine
  whether any slice appears in its training data, which is why its exposure flags
  read \texttt{unknown} and not absent. Every comparison in this paper is
  therefore between deployed systems as a customer reaches them, and a difference
  we attribute to one model may come from its serving stack.
  \item \textbf{The commercial training method is undocumented.} The vendor
  describes its training as RLCD, Reinforcement Learning for Calibrated Decisions,
  and states that it optimises for ``epistemically honest probabilities''
  \citep{typesafe2026jev}. No paper, technical specification, objective function,
  reward definition or training data description has been published, and we have
  not reproduced the method. We therefore cannot test whether the calibration
  behaviour we measure follows from this objective, and we attribute no measured
  behaviour to a training method.
  \item \textbf{Prompt wording is ours.} We wrote the instructions and criteria ourselves; no vendor supplied them. A different phrasing is a different benchmark. We release the exact adapters so the wording is inspectable.
  \item \textbf{One question per request.} This model class is reported to be fastest when many questions share one state. That regime is not measured here, so our latency figures should not be read as the best these systems can do.
  \item \textbf{Serving conditions are not matched.} The commercial model is remote, so its latency includes a network round trip; the open implementation is on a local A100 behind an SSH tunnel, and the 421M model is on a laptop. Latency comparisons are system comparisons.
  \item \textbf{Run-to-run variance is unmeasured.} Each system was run once. Language-model inference is not deterministic by default: even at temperature zero, GPU kernel results depend on how many requests are batched together, which varies with server load \citep{he2025nondeterminism}. We pinned djev to \texttt{seed=0} and \texttt{samples=1}, but it served six requests at a time, and the hosted API exposes no seed or sampling control. Differences smaller than this unmeasured variance should not be interpreted.
  \item \textbf{Training exposure.} Five slices are flagged \texttt{reported} or \texttt{likely}. Results must not be averaged across that flag.
  \item \textbf{Truncation.} 34 ATBench cases and one jailbreak case exceeded the harness cap of 12{,}000 characters and were truncated.
  \item \textbf{Balanced slices do not estimate deployment incident rates.} A prevalence-matched evaluation is required for that claim and is not included.
  \item \textbf{Best-threshold accuracy is optimistic}, chosen on the data it scores.
  \item \textbf{Label polarity is assumed for two sources} whose cards do not state it. We report accuracy under both polarities; in every case the assumed direction was the higher one.
  \item \textbf{\texttt{prompt\_injections} has only 116 cases}, giving intervals roughly 8 points wide. Conclusions drawn from it, including the threshold finding, are correspondingly weaker than those from the 1{,}000-case slices.
  \item \textbf{Laya saw only the first 512 tokens of each ATBench trajectory.} Laya's default context is 512 tokens, and it truncated every ATBench case internally; our truncation flag, which tracks only the harness's own character cap, did not detect this. ATBench trajectories average about 1{,}500 tokens, so Laya's 65.4\% on this slice (Table~\ref{tab:main}) reflects a truncated input and is not directly comparable with the other two systems, which received substantially longer inputs (Table~\ref{tab:context}).
\end{enumerate}
